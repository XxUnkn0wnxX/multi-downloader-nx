# Repository instructions

Read and follow [docs/fork-changes.md](docs/fork-changes.md) before changing this fork or integrating upstream updates. It defines the behavior that `develop` must retain and when an upstream implementation can replace a fork change.

- Keep fork code, this file, and `docs/fork-changes.md` tracked on `develop` and `main`.
- Use `develop` for working changes and `main` as the stable default branch. Promote reviewed changes by fast-forward and preserve the release workflow's tested-source requirements.
- Keep `master-upstream` an exact upstream mirror: sync from `upstream/master` and push to `origin/master-upstream`. This mirror-only sync requires no adaptation or fork-integration plan. Never merge fork changes back into the mirror.
- Maintain `master-upstream`, `develop`, and `main` on the fork's `origin`; upstream feature and Dependabot branches do not need to be copied there.
- Preserve the active changes in the guide during merges and dependency updates. Retire a workaround only after verifying equivalent upstream behavior, and update the guide with that evidence.
- Keep local audit files, credentials, dependency directories, and generated outputs out of commits and generated application files as described in the guide.

## Upstream integration reviews

- These rules apply to bringing upstream changes into the custom fork branches, not to synchronizing the exact upstream mirror.
- Prepare a detailed integration plan before each upstream integration review and before merging or adapting upstream changes into `develop` or `main`. Pin the fork baseline and upstream target SHAs, inventory the proposed changes, and map them to the active contracts in `docs/fork-changes.md`.
- Classify changes for adoption, careful adaptation, or exclusion. Take upstream changes that preserve the fork's behavior; plan overlapping adaptations explicitly and leave unresolved conflicting changes out. Retire a fork repair only after verifying an equivalent upstream implementation with concrete evidence.
- Include dependency and shared-file ordering, compatibility risks, affected CLI/GUI and provider paths, validation gates, documentation updates, rollback steps, and unresolved decisions. Preserve Big Sur compatibility and the documented root, GUI, and generated-application dependency constraints.
- Keep the plan and acceptance evidence current during integration. Verify the final diff and required checks against the planned contracts before promotion or publication, and update the fork guide with what was adopted, adapted, excluded, or retired.

## Provider maintenance and investigation

- Trace the failing layer before changing code: account login/refresh, provider client credentials, playback/download sessions, manifest discovery, or rendition selection. Preserve configured account/resource binding and Big Sur compatibility while investigating.
- Treat an expired access token, a revoked device session, and a rejected Android client credential as separate failures. Use normal refresh with the saved device identity for access-token expiry; request a new device login only when the provider confirms that the saved session cannot refresh. Do not replace a working login or silently switch authentication methods during a probe.
- When the app's request contract has changed, inspect the current official app for the affected platform. For Crunchyroll TV authentication, use the Android TV build; compare phone/tablet builds only when those endpoints are relevant. Prefer an APK from an official installation or publisher-backed distribution. Verify package identity, version/build, TV features, file hash, and signing certificate; a mirror filename or matching hash alone does not prove publisher authenticity or the latest rollout.
- Use the available REA/JADX tooling to inspect the manifest, resources, HTTP service interfaces, client/interceptor setup, serializers, and calling state machines. Trace base URLs, request methods, grant types, device-code fields, client-auth encoding, headers/User-Agent, device identity, polling units, expiry, and refresh behavior through their call sites. Confirm how credentials are constructed instead of guessing a new key, version, or hash from an isolated string.
- Distinguish provider JSON errors from Cloudflare HTML challenges and transport failures. Compare the official HTTPS origin, verified app headers, and actual HTTP negotiation before considering an existing configured fallback. Keep authentication on HTTPS; do not disable certificate checks, replay cookies across unrelated hosts, or change media transport merely to work around an auth failure.
- Keep account tokens separate from temporary playback and download tokens. Bind each manifest/license request and cleanup operation to its own content GUID and session. Track every returned token, release only sessions created by the operation, stop on uncertain cleanup or session/rate limits, and never infer shared ownership from equal PSSH values.
- For manifest or bitrate regressions, inspect provider-returned URLs and MPD/HLS metadata before guessing asset paths. Compare current/legacy families, requested dubs, dimensions, codecs, advertised bandwidth, audio renditions, and declared video timing. Keep optional unavailable legacy families quiet normally and diagnostic under debug; preserve requested audio/subtitle/signs context. Advertised bandwidth and matching durations do not prove file-average bitrate, identical edits, or synchronization.
- Validate the smallest useful stage first: a device code is not an approved login, a successful manifest is not a decrypted download, and a synthetic fixture is not live-service proof. Prefer bounded metadata-only probes and lightweight shared fixtures; avoid media/license requests, account changes, or broad session termination unless authorized for that test.
- Keep APKs, decompiled output, cookies, credentials, signed URLs, live PSSH, and raw transaction captures in ignored local storage. Publish only sanitized findings and necessary reviewed source changes, with provenance and limits stated clearly; never put extracted credentials or private evidence paths in repository guidance.
